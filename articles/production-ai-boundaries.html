Production AI Fails at the Boundaries

Why model changes, untrusted context, and agent economics matter in production.

By Sharmila Das
2026
7 minute read

A lot of AI work begins with the model: Which one should we use? How should we prompt it? Is the benchmark score good enough? Once a feature reaches production, the model is rarely the only concern. Failures often occur between an application and its provider, between model versions, between trusted instructions and retrieved content, or between the economics of a demo and a full workflow.

I treat the model as one dependency inside a larger system. That system must handle change, unreliable inputs, uncertain outputs, and bounded cost.

1. Evaluation is a production control

A regression suite that passes before release shows that a particular configuration met a quality bar at one point in time. It does not establish that behavior will persist.

Providers can update serving behavior and safety layers; retrieval corpora and user behavior change too. Keep a representative, versioned benchmark set and rerun it during releases and on a schedule. Track model and prompt versions, retrieved sources, latency, cost, tool behavior, and quality metrics so a regression can be traced.

For knowledge and content systems, separate retrieval quality from generation quality. Did the system retrieve authoritative evidence? Was the answer grounded in it? Were claims accurate? Did the output follow strategy, policy, and brand constraints?

2. Treat model replacement as lifecycle management

External models are replaceable dependencies. Providers retire versions, introduce successors, change pricing, and alter capability boundaries. Coupling business logic tightly to one model identifier can turn an ordinary upgrade into an emergency.

Use a deliberate model boundary: a thin adapter, normalized inputs and outputs where practical, configuration outside business logic, and a regression suite for candidate replacements. This also allows smaller models for routine work and stronger ones for ambiguous or high-value tasks.

3. Retrieved content is data, not authority

In an agent system, untrusted material includes documents, web pages, email, search results, database fields, API responses, tool output, and uploaded files. Content does not become an instruction merely because a model can read it. Trusted workflow instructions must remain distinct from external evidence.

Controls include provenance, access rules, structured extraction, separation of instructions from evidence, tools with limited permissions, confirmation for sensitive actions, and human approval where risk requires it. The model cannot serve as the sole security boundary.

4. Agent economics are workflow economics

An agent may plan, retrieve, call tools, retry, critique, verify, retain context, and invoke more models before a task completes. Measure cost per successful task, not only per token or call. Repeated cheap calls can form an expensive workflow.

Set maximum steps, bounded retries, context limits, caching, routing by confidence, tool-call limits, timeouts, and stopping conditions. Optimize cost, latency, and quality together.

A stronger production architecture

  1. User or application request
  2. Trust and policy boundary
  3. Orchestration with a cost and step budget
  4. Governed knowledge and retrieval
  5. Model routing and limited tool permissions
  6. Verification and quality gates
  7. Human escalation when risk or confidence calls for it
  8. Observability, continuous evaluation, and feedback

What this means for content and knowledge leaders

Stale knowledge, irrelevant retrieval, unexpected behavior changes, or excessive operating cost can undermine the content experience regardless of how polished the prose looks. Content and knowledge teams should help define authoritative sources, content models, metadata, provenance, freshness, evaluation criteria, risk tiers, and feedback loops.

Engineering owns much of the runtime, but trustworthy context and acceptable output are shared product and content responsibilities.

The metric I would use: cost per trusted outcome

Cost per token is an infrastructure measure. A more useful business measure combines model, retrieval, tool, review, and remediation costs required to finish a task at acceptable quality and risk. A stronger model may reduce retries; better retrieval may shrink context; structured knowledge may improve both quality and efficiency. Human review can be sensible for a small set of high-risk decisions.

What production changes

Production AI requires dependency management, trust boundaries, governed knowledge, permissions, evaluation, observability, fallback behavior, and economic controls. Teams that scale it well design for change, measure continuously, constrain autonomous action, and understand the cost of a completed, trusted task.

Inspired by a practitioner discussion of model behavior changes, forced migrations, prompt injection through external content, and the hidden economics of agent loops. This essay develops those themes for enterprise content and knowledge systems.
