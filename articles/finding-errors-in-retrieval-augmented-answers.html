Retrieval diagnostics

Finding Errors in Retrieval Augmented Answers

A guide to diagnosing problems in sources, search, and generated answers

By Sharmila (Das) Rammohan
2026

Retrieval-augmented generation, or RAG, gives a language model access to information outside its trained parameters. Instead of answering only from patterns encoded during training, the system searches a collection of documents and supplies selected passages to the model as context. This can make answers more current, more specific, and easier to connect to sources [1].

The retrieved material can still be outdated, incomplete, or misinterpreted. To fix an incorrect answer, inspect what the system found and what the model did with it.

The pipeline in five steps

  1. A user asks a question. The system may rewrite or classify it to improve search.
  2. A retriever searches an index and returns candidate passages.
  3. A ranking step selects the passages judged most useful.
  4. The model receives the question, instructions, and selected evidence.
  5. The model produces an answer, which may then be checked, cited, or routed for review.

Keep the question, retrieved passages, ranking results, and generated answer together when investigating a failure. The final answer alone rarely shows where the error began.

Four failures to test

1. The source is relevant but not authoritative

A document may contain the same keywords as the question while relying on second-hand reporting, unverified claims, or an obsolete policy. Semantic similarity is not source authority. A reliable system needs explicit signals such as source type, owner, publication date, review status, and supersession relationships.

2. The passage omits the condition that changes the claim

Suppose a hypothetical API guide says that a request can be retried, while a separate section says that retries require an idempotency key. If chunking separates those passages, the model may recommend a retry without the condition that prevents duplicate work. Check whether the retrieved evidence contains the complete instruction, including its exceptions.

3. The answer goes beyond the evidence

A model may fill a gap in the supplied evidence with a plausible inference. A citation beside the sentence does not prove that the source supports every clause. Check whether the evidence supports the whole claim, supports only part of it, contradicts it, or leaves it unanswered.

4. The system retrieves the right answer from the wrong time

Policies, product specifications, scientific understanding, and organizational decisions change. If the index does not represent versions and effective dates, retrieval may surface content that was once correct. Currency is not simply the date a page was modified; it is the relationship between a claim and the period in which it applies.

What to evaluate

Use separate checks to identify where the answer failed:

  • Source quality: Is the corpus authoritative, current, complete enough for the intended use, and governed by identifiable owners?
  • Retrieval quality: Did the system find evidence that is relevant, sufficient, diverse where necessary, and appropriate to the user’s context?
  • Groundedness: Does each material claim stay within the supplied evidence?
  • Answer quality: Is the response accurate, useful, clear, appropriately qualified, and calibrated to risk?
  • Citation quality: Does each citation support the nearby claim, point to a stable source, and expose enough context for verification?
  • Operational quality: Can the system abstain, route ambiguity to a specialist, and reveal recurring failure patterns?

The RAG paper describes the use of external memory and discusses provenance [1]. Atlas also examines how an updated retrieval index affects model performance [2]. In practice, a team should record which index and source versions produced each test result so it can reproduce a failure after an update.

Turn failures into regression tests

For the retry example, the test should check whether retrieval returns the idempotency requirement and whether the answer includes it. If the passage is missing, inspect chunking and ranking. If it is present but the answer omits it, inspect generation and answer evaluation. Those are separate fixes.

Editors can help specify what a complete answer must include. Engineers can then automate checks that have clear criteria, while subject experts review cases where the source itself is unclear. Keep unresolved cases in the test set rather than treating a plausible answer as a pass.

Decide what happens when evidence is missing

A useful test also covers failure to find enough evidence. The system may need to ask for the product version, state that the source does not answer the question, or route it for review. Choose that behavior before release and test it explicitly.

For each failed answer, ask whether the source was suitable, whether retrieval found the complete evidence, and whether the answer stayed within it. That diagnosis tells the team what to change.
