Diagnostics

When an AI Answer Misses, Check the Whole System

Prompt changes help when the instruction is unclear. They do very little when the system retrieved the wrong source.

By Sharmila Das
2026
5 minute read

An answer uses an old return policy. Someone adds “always use the latest policy” to the prompt and runs it again. The new answer happens to be right, so the incident is closed. A week later, the old policy appears in a different answer.

The prompt change treated the symptom. To prevent the repeat, the team has to find the first layer that allowed the wrong evidence through.

  1. SourceWas the correct information available, current, and approved?
  2. RetrievalDid search select the right material and version?
  3. ContextDid the system preserve the useful evidence and remove distracting material?
  4. GenerationDid the model understand the task and follow the constraints?
  5. EvaluationDid the tests detect the error before release?
  6. ReviewDid the workflow send the answer to the right person when judgment was required?

Name the failure without diagnosing it

Write down what happened in plain language. “The answer used an old return policy” is more useful than “the model hallucinated.” “The draft ignored the approved message for new customers” gives the team something it can reproduce.

Diagnosis comes next. Find the first point where the process could have prevented the error. If the current policy never entered the knowledge base, prompt work comes too late. If retrieval selected the old policy even though the current one was available, ranking, metadata, and version rules deserve attention.

Source problems often look like model problems

Teams sometimes expect the model to resolve a conflict people have never settled. Two pages define the same product differently. A policy changes without an effective date. A claim appears in several documents and nobody owns it.

That repair is content work: choose the source of record, name the owner, retire old material, and record where the information applies. No prompt can supply a decision the organization has avoided making.

Retrieval can be wrong in quiet ways

Search can return material that is relevant by topic and wrong for the request. An answer for an existing customer may use acquisition messaging. A global search may retrieve guidance for the wrong market. A similar product name may pull in an unrelated procedure.

Inspect the sources that were returned, their order, and the filters applied. The source list usually explains more than another close reading of the final prose.

A fluent answer can hide a retrieval mistake. The source list usually cannot.

Context can lose the useful part

Even good retrieval can produce poor context. The key limitation may be cut off. A long document may crowd out a short but critical policy. Near-duplicate passages may consume the space needed for better evidence.

Look at the context exactly as the model received it. Is the important statement present? Did its qualifiers stay attached? Is less useful text taking up the window? A citation to the right document does not guarantee the model saw the right passage.

Generation problems are real and specific

Once the source and context hold up, the prompt becomes a useful suspect. The task may be ambiguous. The output format may be missing. The instruction may ask for a recommendation without naming the criteria.

Change one thing at a time and rerun a small set of known examples. A prompt that grows after every incident soon becomes its own debugging problem.

Evaluation should point to a repair

A single quality score does not tell the team what to repair. Separate factual accuracy, source use, audience fit, policy compliance, and task completion. A failure should carry a reason and a destination.

Repeated source failures belong with content owners. Retrieval failures belong with search and knowledge teams. Review failures may point to routing or decision rights. Without that handoff, evaluation produces dashboards instead of improvements.

A short incident note is enough

For each meaningful failure, record the request, the answer, the sources, the failed layer, the correction, and the owner. The note can be brief. Its value comes from making repeated patterns visible across incidents.
