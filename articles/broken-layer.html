Diagnostics

When an AI Answer Misses, Check the Whole System

Prompt changes help when the instruction is unclear. They do very little when the system retrieved the wrong source.

By Sharmila Das
2026
5 minute read

A weak answer often starts a familiar cycle: rewrite the prompt, add another instruction, and try again. Sometimes that works. Sometimes the new prompt only hides a problem somewhere else.

I use a six-part diagnostic to keep the investigation focused. The goal is to identify the team and component that can prevent the failure from returning.

  1. SourceWas the correct information available, current, and approved?
  2. RetrievalDid search select the right material and version?
  3. ContextDid the system preserve the useful evidence and remove distracting material?
  4. GenerationDid the model understand the task and follow the constraints?
  5. EvaluationDid the tests detect the error before release?
  6. ReviewDid the workflow send the answer to the right person when judgment was required?

Begin with the failure you can see

Write down what is wrong in plain language. “The answer used an old return policy” is more useful than “the model hallucinated.” “The draft ignored the approved message for new customers” gives the team a testable issue.

Then identify the first point where the process could have prevented it. If the current return policy never entered the knowledge base, prompt work comes too late. If retrieval selected the old policy despite the correct version being available, investigate ranking, metadata, and version rules.

Source problems often look like model problems

Teams sometimes expect the model to resolve a conflict that people have never settled. Two pages may define the same product differently. A policy may have changed without an effective date. A claim may appear in several documents with no owner.

The repair is content work: choose the source of record, name the owner, retire old material, and record the conditions under which the information applies.

Retrieval can be wrong in quiet ways

The system may find material that is relevant by topic and wrong for the request. An answer for an existing customer may use acquisition messaging. A global search may return guidance for the wrong market. A similar product name may pull in an unrelated procedure.

Look at the actual sources returned, their order, and the metadata used to filter them. This is usually more revealing than reading the final answer alone.

A fluent answer can hide a retrieval mistake. The source list usually cannot.

Context can lose the useful part

Even good retrieval can produce weak context. The key limitation may be cut off. A long document may crowd out a short but critical policy. Several near-duplicate passages may leave too little room for the evidence that matters.

Inspect the context exactly as the model received it. Check whether the important statement appears, whether its qualifiers remain attached, and whether less useful text is taking up space.

Generation problems are real and specific

Once the sources and context are sound, the prompt becomes a more useful place to look. The task may be ambiguous. The output format may be missing. The instruction may ask for a recommendation without saying which criteria matter.

Change one thing at a time and test against a small set of known examples. A longer prompt can make a system harder to understand if nobody knows which instruction changed the result.

Evaluation should point to a repair

A single quality score tells the team very little. Separate factual accuracy, source use, audience fit, policy compliance, and task completion. A failed check should identify what went wrong and where the issue should be sent.

Use the results to build a backlog. Repeated source failures belong with content owners. Retrieval failures belong with search and knowledge teams. Review failures may require clearer routing or decision rights.

A short incident note is enough

For each meaningful failure, record the request, the answer, the sources, the failed layer, the correction, and the owner. This small habit turns scattered debugging into evidence about where the system needs work.
