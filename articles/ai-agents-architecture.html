Agent architecture

AI Agents Need Architecture, Not Just Better Prompts

Reliable enterprise agents depend on knowledge, tools, state, controls, and feedback.

By Sharmila Das
2026
7 minute read

The first wave of generative AI taught organizations to focus on prompts. That made sense when the task was mostly conversational: ask a model a question, get an answer, refine the instruction, and try again. Agents change the problem. An agent is expected to understand a goal, decide what to do next, find the right information, use tools, preserve state, act within permissions, recover from failure, and know when to stop or ask for help.

The model is only one component

A capable language model can reason over the context it receives, but it does not automatically know which enterprise source is authoritative, whether a policy has changed, what happened earlier in a workflow, which system it may modify, or whether an action succeeded. Reliability comes from the surrounding design.

A practical agent architecture

1. Goal and orchestration

Translate the user's objective into a bounded workflow. Decide which steps can be automated, what completion means, and when the agent must escalate.

2. Governed knowledge

Give the agent authoritative product facts, policies, audience definitions, approved claims, terminology, and operating rules. Authority, freshness, ownership, and versioning matter as much as retrieval.

3. Retrieval and context construction

Retrieve only the evidence needed for the current step. Metadata, semantic and keyword retrieval, relationships, reranking, source authority, and access controls help construct compact, useful context.

4. State and memory

Maintain what the agent has learned, decisions made, tool results, open questions, and workflow status. Persistent memory should be deliberate rather than an uncontrolled transcript dump.

5. Tools and actions

Connect APIs, search, databases, and content systems through defined interfaces. Schemas, validation, retries, idempotency, and error handling determine whether the agent can act safely.

6. Permissions and policy

Constrain what the agent may see and do. Authentication, authorization, data boundaries, personal information handling, approval requirements, and risk classification belong in the architecture.

7. Evaluation and verification

Check evidence sufficiency, grounding, action success, and business rules. Some checks can be deterministic; others need model evaluation or expert review.

8. Observability and recovery

Capture traces, tool calls, latency, errors, cost, retrieval behavior, quality scores, and escalations. A production agent needs a controlled path to retry, compensate, or hand off.

The architecture in one flow

  1. User goal and bounded plan
  2. Governed knowledge and retrieval
  3. Context and state
  4. Model reasoning and authorized tool action
  5. Verification and quality gates
  6. Next step, human escalation, or completion
  7. Observability and feedback into system improvement

Why content and knowledge architecture become strategic

If an agent creates customer-facing content or makes decisions, the organization cannot rely on a pile of documents and hope retrieval finds the right paragraph. Knowledge must be designed for machine use: reusable content objects, metadata, taxonomies, ontologies, entity relationships, source-of-truth rules, approval status, versioning, and retrieval constraints.

Audience definitions, value propositions, approved claims, proof points, brand guidance, product facts, channel rules, and policy become structured knowledge the agent can apply. Content strategy moves upstream to design the environment that makes sound outputs repeatable.

An example: an AI marketing agent

Imagine a marketer asks an agent to create an SMB campaign for a market and channel. A weak implementation sends the request to a model with a long prompt and a folder of documents. A stronger workflow identifies the audience and objective; retrieves current claims and proof; applies brand and policy constraints; generates a brief and variants; checks grounding and accuracy; routes higher-risk work for review; publishes through an authorized tool; and uses performance data to improve evaluation.

The gain is a repeatable operating system for strategy, knowledge, governance, and quality.

Prompt engineering becomes a small part of the system

Clear instructions and tool descriptions matter. Their benefit is limited when authoritative knowledge, retrieval, state management, permissions, evaluation, or recovery is missing. A useful design question is: What does the system need at this step to make a sound decision?

The enterprise advantage is outside the model

As foundation models become broadly available, differentiation moves into proprietary knowledge, structured context, workflow design, evaluation data, governance, integrations, and feedback loops. The best agent operates with the right knowledge, appropriate permissions, explicit quality standards, visible behavior, and a safe path when confidence is low.

What leaders should ask before deploying an agent

  • What may the agent decide or change?
  • Which sources are authoritative, current, and versioned?
  • How is context constructed for each step?
  • What state persists, and what should not be remembered?
  • How are tool calls validated and failures recovered?
  • Which decisions require checks or human approval?
  • How are quality, task completion, cost, and impact measured?
  • Can we reconstruct what the agent saw, decided, and did?

Where this is heading

The move from copilots to agents is a move from generation to execution. The disciplines that make information findable, reusable, governed, consistent, and measurable are becoming core infrastructure for AI.
