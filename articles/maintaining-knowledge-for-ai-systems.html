Knowledge maintenance

Maintaining Knowledge for AI Systems

Source ownership and maintenance affect the answers people receive

By Sharmila (Das) Rammohan
2026

Consider a hypothetical support assistant answering a question about a product feature. It finds a clear explanation in an old release guide and repeats it accurately. The answer is still wrong for the customer’s current version. A better prompt might ask the model to check the version, but the system also needs a way to identify which guide applies and whether a newer source replaces it.

This is a content maintenance problem as well as a retrieval problem. When an organization connects an assistant to its documentation, it needs to decide which sources the assistant can use, who maintains them, and what happens when they conflict. Leaving those decisions implicit makes errors harder to diagnose.

The model’s behavior is one part of reliability. The condition of the source collection matters too.

Record which source applies

People familiar with a product often know which document to trust. They may remember that a feature changed in the last release or know whom to ask about an exception. That knowledge is easy to lose when documents pass into an index without their version history or ownership records.

For a product knowledge base, each source should identify its owner, applicable version, review date, and status. A policy collection may also need effective dates and jurisdiction. These fields should reflect the questions the assistant must answer. More metadata is useful only when it helps select or interpret a source.

Retrieval-augmented generation gives language models access to external information [1]. It makes the source collection available during answering, but the organization still has to maintain that collection. Search cannot reliably resolve conflicting policies if neither record says which policy is in force.

Make source context visible

Readers need enough source information to decide whether an answer applies to them. In the support example, the product version may matter more than the date a page was last edited. For a research finding, the study population and test conditions may be essential.

The explanation should match the decision. A routine product question may need a link and a version label. A recommendation that could affect someone’s health, finances, or rights needs clearer limits, including what the system cannot determine and when a specialist should review it.

Model cards provide a useful precedent for documenting intended uses, evaluation conditions, and limitations [2]. The same attention to context helps readers interpret knowledge-based answers. A result without its conditions can be easy to misread.

Assign editorial responsibilities

Editors and subject experts should agree on which sources are approved for use and which claims need qualification. Engineers need those decisions in a form the system can apply, such as a version filter, a review status, or a rule for handling conflicting sources.

For example, an editor might find that two pages use different definitions of the same feature. The subject expert resolves the difference; the content owner updates the pages; Engineering tests whether retrieval now selects the correct explanation. Recording those decisions prevents the same error from returning with the next ingestion.

NIST’s generative-AI risk profile treats risk management as work across the system lifecycle [3]. Source selection and maintenance deserve that ongoing attention. A review at launch cannot account for every policy or product change that follows.

Test maintenance as well as launch readiness

A test set should include questions whose answers change over time. After a release or policy update, the team can check whether the assistant uses the new source, preserves an exception, and stops citing the retired document.

When an answer fails, record the cause and the owner of the fix. A missing version field, an ambiguous passage, and a model that ignores supplied evidence require different changes. Treating every failure as a prompt problem leaves the source defects in place.

Start with the sources people use most

For a first rollout, I would check five things:

  1. Each approved source has a named owner and a review schedule.
  2. Versions and effective dates identify when a claim applies.
  3. Answers show the source context needed for the user’s decision.
  4. Tests cover source changes, retrieval errors, and unsupported claims.
  5. Questions the assistant cannot resolve have a defined review path.

Start with a small collection that the team can maintain. Expand it after the tests show that answers remain useful when the sources change. That gives content owners a manageable workload and makes failures easier to trace.
