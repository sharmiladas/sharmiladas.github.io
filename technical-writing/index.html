01 · Engineering article · Independent prototype

The request timed out. Did the job get created?

A client sends a request to create an indexing job. The service commits the job, but the connection closes before the response reaches the client. The client sees a timeout. The database sees a successful insert. Retrying an ordinary create operation can now produce a second job.

The retry needs an identity that survives the lost response. In this prototype, the client supplies an idempotency key. The service stores that key alongside a fingerprint of the request and the response it would have returned. A repeated request with the same key and payload receives the stored result.

Commit the job and replay record together

Saving the job and saving its retry record in separate commits leaves a gap: the first write can succeed while the second fails. The example uses one database transaction for both. A failure before commit rolls them both back. The transaction covers these two database writes. An external worker’s actions require their own failure handling.

The replay identity is the pair (tenant, key). Scoping the key prevents two tenants using the same string from sharing a response. The fingerprint prevents a different request from silently reusing an old result. The example hashes JSON serialized with sorted keys and compact separators using SHA-256. A real API must define normalization: omitted defaults, number formats, and API versions can change whether two bodies represent the same operation.

with db:
    prior = lookup(tenant, key)
    if prior:
        verify_same_fingerprint(prior, payload)
        return prior.response
    job = insert_job(payload)
    store_replay_record(tenant, key, payload, job)
    return job

Control-flow excerpt. The complete executable implementation is in examples.py; the helper names above are explanatory.

What the tests show

TestObserved behaviorUntested behavior
Replay the same requestSame job ID; one job rowConcurrent requests on separate connections
Reuse key with changed payloadValueError; existing job unchangedAn HTTP status or complete error contract
Reuse key across tenantsDistinct jobsAuthentication or authorization
Fail before commitNo job or replay row remainsCrash recovery, storage failure, or failover

What changes in a service

The prototype runs serially on one SQLite connection. A production implementation needs a unique constraint and a deliberate strategy for concurrent arrivals. Do not assume that a read followed by an insert wins a race. PostgreSQL’s transaction-isolation documentation describes how competing writes and conflict handling behave; the service must handle its chosen isolation level and retry conditions [1].

If the next step calls an external queue or payment provider, the database transaction cannot automatically roll back that external action. One design option is to commit an outbox event with the job, then have a worker deliver it with deduplication at the receiving boundary. That moves the retry problem; it does not remove it.

The API contract also needs a retention period for keys, behavior while an operation is still pending, and a policy for failed requests. Expiring a key too early allows a delayed retry to create new work. Keeping every response forever creates storage and privacy costs. Choose the window from client retry behavior and the operation’s risk, then test the boundary.

Sources

[1] PostgreSQL 18: Transaction Isolation. [2] Python sqlite3 documentation. The prototype uses a connection context manager for commit/rollback. These sources explain the database mechanisms used here.

02 · Failure analysis · Synthetic fixture

The right words, the wrong product version

A search result can match a question perfectly and still be unusable. The fixture in this sample contains two invented API instructions. Version 1 permits a retry without a key. Version 2 requires an idempotency key. Both contain the words “retry upload requests.” A simple lexical ranker gives them the same score and returns the older record because it appears first.

The two-document fixture isolates a selection error: both records match the query, but only one applies to the requested version.

Reproduce the failure

question = 'Retry upload requests'
retrieve(question)                 # selects v1
retrieve(question, version='2')    # selects v2
retrieve(question, version='3')    # returns None

The correction filters candidates by version before ranking them. Filtering only after selecting the top result can discard the answer without recovering the relevant document that ranked below it. In a larger system, applicability might include locale, account permissions, effective date, and product tier.

Check the selected source and its required condition

The tests check which source was selected and whether its text includes the idempotency requirement. Both checks inspect retrieved text. To evaluate a generated answer, a separate test would need to compare the answer’s claims with that evidence.

ConditionFixture resultInterpretation
No version filterv1 selectedLexical match is insufficient
Version 2 filterv2 selected with key requirementApplicability narrows eligible evidence
Unknown versionNo evidence returnedCaller must clarify, abstain, or escalate

A missing result should remain missing

For version 3, neither document is applicable. Silently falling back to version 1 would hide uncertainty behind a confident answer. The retrieval function returns no evidence. The caller needs an explicit policy: ask for a supported version, point to a maintained source, or state that the collection does not answer the question.

That policy has a cost. Strict filters can reduce coverage when metadata is incomplete. Relaxing them improves recall but risks using the wrong source. A practical rollout should log no-evidence cases separately from incorrect-source cases, so content owners can distinguish missing coverage from bad selection.

What a larger evaluation would need

Use a versioned question set with expected source IDs, required answer conditions, and examples where no answer is available. Freeze the corpus and retrieval configuration for each run. Measure retrieval and answer quality separately. Include permission-sensitive cases without putting private documents or identifiers into a public report.

The original RAG research combines parametric and retrieved memory and reports improvements on its evaluated tasks [1]. Here, the fixture tests lexical selection and version filtering. Evaluating a RAG system would also require a generator and an answer-quality test set.

Source

[1] Lewis et al. (2020), Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks. Product versions and retry instructions in this sample are invented test data, not real API guidance.

03 · Code walkthrough · Workflow infrastructure

Reject a broken workflow before running it

A workflow describes three tasks: build an artifact, test it, then publish it. If testing depends on publication and publication depends on testing, no task can satisfy its prerequisites. A runner that discovers this after allocating workers wastes resources and may leave partial work behind.

This prototype treats a workflow as a directed dependency graph. A compilation step validates its references and produces an ordered plan before any task executes. It rejects cycles and missing dependencies rather than guessing an order.

Separate “being explored” from “finished”

The algorithm tracks two sets. A node in the visiting set belongs to the active traversal path. Reaching it again indicates a cycle. A node in the visited set is already complete; reaching it again is allowed because several tasks may share a prerequisite.

def visit(node):
    if node not in graph:
        raise ValueError('missing dependency: ' + node)
    if node in visiting:
        raise ValueError('cycle: ' + node)
    if node in visited:
        return
    visiting.add(node)
    for dependency in sorted(graph[node]):
        visit(dependency)
    visiting.remove(node)
    visited.add(node)
    order.append(node)

Appending after visiting dependencies puts prerequisites before their consumers. Sorting names makes the plan deterministic for the same graph. That helps compare plans during review, although alphabetical order is not a scheduling policy. The full implementation also visits disconnected components.

Why validate before scheduling?

ApproachBenefitTradeoff
Validate as tasks arriveCan accept dynamic workErrors may emerge after execution begins
Compile a complete graph firstRejects structural defects before side effectsRequires a known graph or staged recompilation
Use a mature workflow engineCan supply persistence and scheduling featuresIntroduces integration and operating requirements

For this fixed educational graph, a compile-first design is easy to inspect. The tests verify a dependency chain, a cycle, a missing node, and a shared prerequisite appearing once. Recovery of a running workflow remains untested.

What the runner still needs

The compiler does not manage worker capacity, retries, durable task state, cancellation, or secrets. Independent tasks could run in parallel, but this sample returns only an order. A production scheduler would need to maintain readiness as tasks complete and persist the state transitions it depends on.

Recursion is another limit. Deep dependency chains can exceed Python’s recursion limit. An iterative traversal or an indegree-based algorithm avoids dependence on the call stack. This implementation also sorts nodes and dependency lists; its cost therefore includes sorting, rather than being strictly linear in graph size.

Before adding a runner, define what completion means. A process returning zero may not prove that the expected artifact exists. For the build-test-publish chain, task outputs and validation criteria should be explicit. Otherwise the graph can be structurally correct while the workflow publishes the wrong thing.

04 · Worked editorial sample

From rough engineering notes to a defensible article

Constructed notes for editing practice.

Source notes

“Retries fixed. Key stored in DB. Tested repeat calls. No duplicates. Should be safe now. One transaction. Need queue next. Probably exactly once.”

Edited passage

“The prototype stores a job and its replay response in one database transaction. When a client repeats the same request with the same tenant-scoped key, the service returns the existing job ID. A local test confirmed that two serial calls created one job row. Concurrent requests remain untested. Queue delivery also requires a separate failure and deduplication design.”

Editing decisions

Original wordingEditReason
Retries fixedDescribe key lookup and response replayExplain the mechanism, not just the outcome
No duplicatesTwo serial calls created one rowBound the claim to the actual test
Safe nowIdentify untested concurrent requestsAvoid an undefined safety assurance
Exactly onceSeparate creation from external executionDistinguish database atomicity from distributed delivery

Questions before publication

  • Where does the replay response commit relative to the job?
  • What happens when two connections present the same new key?
  • How long are keys retained, and what happens after expiration?
  • What happens if queue delivery succeeds but its acknowledgement is lost?
  • Which failures were reproduced, and which remain assumptions?

The revision preserves the useful finding without turning a small test into a production guarantee. The unanswered questions stay in the review record; they are not filled with plausible details.

Editorial method

Find the engineering story before drafting

A useful engineering article usually has a decision at its center. Start with the constraint that made the obvious solution insufficient, then investigate the alternatives, the failure, and the evidence that changed the team’s approach.

AskRequest as evidenceUse in the article
Which invariant could not be broken?Contract, design note, failing testState the problem precisely
What simpler design was rejected?Decision record and comparisonExplain the tradeoff
Where did the first approach fail?Sanitized trace or reproductionShow the failure mechanism
What changed after the fix?Comparable runs and methodologyReport a bounded result
What still does not work?Known issues and reviewer notesMake limitations visible

Before release, confirm technical interpretation with the engineer, rerun the published examples, and check diagrams against the implementation. Record what each measurement means, including the workload and environment. If there is no evidence for a number, omit it.

Reproducibility & disclosure

"""Small, deterministic demonstrations. Not a production service."""
import hashlib
import json
import re
import sqlite3
import unittest


def database():
    db = sqlite3.connect(':memory:')
    db.executescript('''
        CREATE TABLE requests (
            tenant TEXT, key TEXT, digest TEXT NOT NULL,
            response TEXT NOT NULL, PRIMARY KEY (tenant, key));
        CREATE TABLE jobs (id INTEGER PRIMARY KEY, payload TEXT NOT NULL);
    ''')
    return db


def create_job(db, tenant, key, payload, fail=False):
    serialized = json.dumps(payload, sort_keys=True, separators=(',', ':'))
    digest = hashlib.sha256(serialized.encode()).hexdigest()
    # A single connection, serial execution; not a concurrency benchmark.
    with db:
        prior = db.execute(
            'SELECT digest, response FROM requests WHERE tenant=? AND key=?',
            (tenant, key)).fetchone()
        if prior:
            if prior[0] != digest:
                raise ValueError('key reused with a different payload')
            return json.loads(prior[1])
        cursor = db.execute('INSERT INTO jobs(payload) VALUES (?)', (serialized,))
        response = {'job_id': cursor.lastrowid}
        db.execute('INSERT INTO requests VALUES (?, ?, ?, ?)',
                   (tenant, key, digest, json.dumps(response)))
        if fail:
            raise RuntimeError('simulated failure before commit')
        return response


DOCS = [
    {'id': 'v1', 'version': '1', 'text': 'Retry upload requests without a key.'},
    {'id': 'v2', 'version': '2', 'text': 'Retry upload requests with an idempotency key.'},
]


def retrieve(question, version=None):
    # Lexical baseline, deliberately not embedding search or a real RAG model.
    terms = set(re.findall(r'\w+', question.lower()))
    candidates = [d for d in DOCS if version is None or d['version'] == version]
    ranked = sorted(candidates, key=lambda d: -len(
        terms & set(re.findall(r'\w+', d['text'].lower()))))
    return ranked[0] if ranked else None


def compile_graph(graph):
    """Return a stable topological order or reject cycles/missing references."""
    order, visiting, visited = [], set(), set()

    def visit(node):
        if node not in graph:
            raise ValueError('missing dependency: ' + node)
        if node in visiting:
            raise ValueError('cycle: ' + node)
        if node in visited:
            return
        visiting.add(node)
        for dependency in sorted(graph[node]):
            visit(dependency)
        visiting.remove(node)
        visited.add(node)
        order.append(node)

    for node in sorted(graph):
        visit(node)
    return order


class PortfolioTests(unittest.TestCase):
    def test_retry_creates_one_job(self):
        db = database()
        first = create_job(db, 'a', 'k', {'task': 'index'})
        self.assertEqual(first, create_job(db, 'a', 'k', {'task': 'index'}))
        self.assertEqual(db.execute('SELECT COUNT(*) FROM jobs').fetchone()[0], 1)

    def test_changed_payload_rejected(self):
        db = database()
        create_job(db, 'a', 'k', {'task': 'index'})
        with self.assertRaises(ValueError):
            create_job(db, 'a', 'k', {'task': 'delete'})

    def test_tenant_scoping(self):
        db = database()
        self.assertNotEqual(create_job(db, 'a', 'k', {}), create_job(db, 'b', 'k', {}))

    def test_rollback(self):
        db = database()
        with self.assertRaises(RuntimeError):
            create_job(db, 'a', 'k', {}, fail=True)
        self.assertEqual(db.execute('SELECT COUNT(*) FROM jobs').fetchone()[0], 0)
        self.assertEqual(db.execute('SELECT COUNT(*) FROM requests').fetchone()[0], 0)
        self.assertEqual(create_job(db, 'a', 'k', {})['job_id'], 1)

    def test_unfiltered_retrieval_selects_old_version(self):
        self.assertEqual(retrieve('Retry upload requests')['id'], 'v1')

    def test_filter_preserves_required_condition(self):
        result = retrieve('Retry upload requests', version='2')
        self.assertEqual(result['id'], 'v2')
        self.assertIn('with an idempotency key', result['text'])

    def test_unknown_version_has_no_evidence(self):
        self.assertIsNone(retrieve('Retry upload requests', version='3'))

    def test_graph_order(self):
        self.assertEqual(compile_graph({'publish': ['test'], 'test': ['build'], 'build': []}),
                         ['build', 'test', 'publish'])

    def test_cycle_rejected(self):
        with self.assertRaises(ValueError):
            compile_graph({'a': ['b'], 'b': ['a']})

    def test_missing_dependency_rejected(self):
        with self.assertRaises(ValueError):
            compile_graph({'build': ['missing']})

    def test_shared_dependency_once(self):
        order = compile_graph({'a': ['base'], 'b': ['base'], 'base': []})
        self.assertEqual(order.count('base'), 1)
        self.assertLess(order.index('base'), order.index('a'))
        self.assertLess(order.index('base'), order.index('b'))


if __name__ == '__main__':
    unittest.main(verbosity=2)
