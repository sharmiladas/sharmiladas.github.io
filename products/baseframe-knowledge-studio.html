Baseframe Knowledge Studio

A local workspace that connects documents, source evidence, reviewed relationships, and an entity wiki.

By Sharmila Das
October 2026
Working local MVP
Python · SQLite · JavaScript

Current status: A local, single-user prototype with persistent document storage, keyword evidence search, a graph, and a review queue.

The source repository is private. Its run guide requires GitHub access. The main workspace runs without an API key. It is separate from the earlier browser-only graph editor.

Source repository · private ↗Complete run guide · access required ↗

The problem

Documentation teams can find a page without finding the relationship they need: which system a product depends on, who owns it, or which policy governs it. A useful knowledge tool must preserve the source behind a relationship and make its approval visible.

The product decision

I scoped the first version around documentation and content platform teams. The initial task is small: add a platform charter, inspect the proposed relationships, approve the ones supported by the text, and use that knowledge to find dependencies and owners.

The design connects discovery to review. Source passages remain visible throughout the workflow, and new relationships enter a pending state. Search returns the passages it finds; it does not turn them into an unsupported generated answer.

What I built

CapabilityCurrent behavior
Document workspacePaste source text or upload text and Markdown files. Store documents in SQLite.
Relationship candidatesRecognize explicit English statements using seven controlled relationship phrases. Retain the exact source quote.
Human reviewApprove or reject each relationship after inspecting its meaning and evidence.
Knowledge graphVisualize approved relationships and inspect an entity’s source evidence.
Entity wikiBuild linked entity views from approved relationships and their quotations.
Evidence searchReturn keyword-matching source passages with document citations and a no-evidence state.
PortabilityExport an evidence snapshot as JSON. Back up the full workspace by copying its database while the server is stopped.

The user journey

  1. Add: Ingest a document such as a content platform charter.
  2. Inspect: Read the extracted candidate and its exact quotation.
  3. Review: Approve meaning, entity identity, and relationship direction.
  4. Explore: Follow approved connections in the graph or entity wiki.
  5. Find evidence: Search for a question and inspect the cited passages.

An illustrative source sentence, “Content Advisor depends on CMS,” creates a pending depends_on relationship. It appears in the approved graph only after review. This is demo data, not a claim about an employer’s systems.

Architecture

The browser calls a local Python API. The API stores documents and relationship decisions in SQLite, extracts explicit relationships, and retrieves matching passages. The browser builds the graph and wiki from approved records.

Browser workspace

Documents, review queue, evidence search, graph, wiki, and JSON export.

Local Python API

Document ingestion, controlled extraction, quote checks, review updates, and keyword retrieval.

SQLite persistence

Source documents and relationship records, including quotes and approval state.

The local server binds to 127.0.0.1. Mutation requests check the host and origin. UI text is escaped, and input sizes are bounded. These controls support a local prototype; they do not provide enterprise identity or document permissions.

Tradeoffs I made

  • Start with explicit relationships: Controlled extraction makes candidate behavior inspectable. It misses statements outside the supported grammar.
  • Keep retrieval extractive: Showing source passages makes evidence visible. Keyword matching cannot reliably interpret paraphrases.
  • Use SQLite: A single local database keeps setup simple. It does not solve shared access or a production graph service.
  • Separate AI extraction: The optional CLI produces model-assisted candidates for the earlier graph editor. Integration into the persistent workspace remains a next step.

How to run it

Download the repository, open a terminal in its folder, and run:

python3 server.py

On Windows, use py server.py. Then open http://127.0.0.1:8000. Python 3.10 or newer is required. No dependency installation or API key is needed for the main workspace.

Start with Add sample charter in Overview, approve relationships in Review queue, then open Knowledge graph, Wiki, and Ask knowledge.

What I verified

Five Python tests passed for document persistence, extraction validation, missing evidence, and no-answer behavior. JavaScript checks passed for quote validation, malformed graph imports, approval downgrades, and directed paths in the earlier editor. An HTTP smoke check passed for serving the workspace, adding a document, approving a relationship, and retrieving its source passage.

These checks establish basic behavior. Customer adoption, task completion time, semantic accuracy at scale, and live model extraction have not been measured or verified.

What comes next

The next product gate is a small retrieval pilot: representative questions, expected sources, unsupported questions, and a comparison against the current search workflow. That evidence should guide whether to add embeddings, hybrid retrieval, and cited answer generation.

Later phases include shared ingestion for the CLI and UI, entity resolution, source versions, document deletion and update propagation, review history, authentication, and document-level permissions.

Implemented: Local document workspace, controlled extraction, review, keyword retrieval, graph, wiki, and exports.

Planned: PDF/Word parsing, semantic retrieval, generated answers in the persistent workspace, connectors, synchronization, and team access.
