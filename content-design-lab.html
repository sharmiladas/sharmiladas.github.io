Prompts Are Content Design Specifications

By Sharmila Das

A prompt starts with a decision about what someone needs to understand or do. The model instruction comes later. If the user problem is unclear, more elaborate instructions can produce consistent output that solves the wrong problem.

Consider a fictional writing assistant onboarding a new user. “Write engaging onboarding copy” leaves several decisions unresolved. What can the product actually do? What does the user need to supply? What happens after the button? What should the system avoid promising?

A useful brief answers those questions before generation. The product can revise text supplied by the user. The person needs to paste a paragraph and choose a goal. Suggestions remain optional. The message should make that next action understandable without promising a better grade, a job offer, or another unsupported result.

The prompt can then encode the design: approved facts, audience, user state, action, voice, constraints, and output structure. “Paste a paragraph to begin” follows from the interaction. It is not simply a friendlier version of a vague instruction.

Documentation transformation makes this relationship especially visible. A prompt must preserve more than meaning in the abstract. Commands, parameter names, prerequisites, version conditions, and warnings may carry functional consequences. The instruction should identify what can change, what must remain intact, and when an uncertainty requires review.

The first output is a design test. Suppose a transformed document loses a prerequisite. Adding “be accurate” gives little guidance. A stronger revision identifies prerequisite preservation explicitly, includes a representative example, and requires an issue report when source material is incomplete. The revised prompt then needs regression testing against cases it previously handled well.

This creates a practical division of responsibility. Content design defines acceptable communication and the user task. Engineering implements the repeatable workflow. Evaluation tests whether the resulting behavior meets the specification. Each contributes to a usable system.

For a portfolio, show that chain. Include a brief, an initial prompt, a failed output, the reasoning behind a revision, and the results of a controlled comparison. Describe failures that remain. The strongest evidence is a defensible design decision that changed system behavior.

Try it: Choose one message. Write its user job, source boundary, required action, and three failure conditions. Build two prompt versions and explain the specific behavior each change is intended to improve.

Turn Editorial Judgment into an Evaluation People Can Use

By Sharmila Das

“This copy feels wrong” can be the start of useful feedback. It cannot be the entire evaluation system. A repeatable assessment needs to identify what failed, why it matters, and what evidence would support a different judgment.

Start with the user task. An onboarding message should help a person understand the next action. A recovery message should explain a problem and a workable next step. A notification should provide enough value to justify an interruption. Those purposes require different criteria even when all three messages share the same voice.

Next, separate dimensions. Clarity asks whether the meaning is understandable. Grounding asks whether claims have support. Context asks whether the message fits the person's state. A clear message can still be factually wrong. One combined “quality” score can hide that distinction.

Use anchored judgments. A clarity score of zero might mean the intended action is unclear. One could mean the action is understandable after interpretation. Two could mean the next action is explicit and appropriate. Reviewers need examples at the boundary, including cases with more than one acceptable wording.

Some failures should block release regardless of the average. An invented product capability is not repaired by excellent tone. A notification that exposes sensitive information is not rescued by a short headline. Decide which failures are gates before examining candidate results.

Then design the dataset. Include ordinary use, sparse context, conflicting source material, already-completed tasks, and known failure patterns. Label the expected behavior instead of forcing every output to resemble one reference sentence. Divide scenario families between development and held-out assessment so near duplicates do not create an exaggerated impression of generalization.

The result should help people act. A report that says “quality fell” is less useful than one showing that missing prerequisites increased in recovery scenarios after a prompt change. That finding points to a specific investigation and a regression test.

For a small portfolio project, publish the rubric, scenario coverage, failure examples, and release recommendation alongside the aggregate results. Explain the sample's limits. A carefully documented small evaluation demonstrates judgment; it does not establish production-wide performance.

Try it: Write a six-dimension rubric for five fictional messages. Add two hard gates. Ask another reviewer to apply it independently, then identify which definitions produced disagreement.

Reference: OpenAI's evaluation best practices provides general background on task-specific assessment. The rubric and gates in the companion toolkit are proposed exercise rules.

Test the Evaluator Before Trusting the Score

By Sharmila Das

An automated grader can make content review faster while creating a new source of error. It may reject useful content, overlook a serious defect, or apply the same criterion inconsistently. A quality score becomes useful only when we understand the behavior behind it.

Begin with a reference. Two reviewers independently examine the same examples using written criteria. Preserve their initial judgments. Discuss disagreements afterward and record a separate adjudicated decision. Otherwise, the process can confuse consensus achieved through discussion with independent agreement.

Human disagreement is informative. If reviewers disagree about whether a claim is supported, the source boundary may be unclear. If they disagree about tone, the rubric may need examples. Do not automatically treat the majority opinion as an unquestionable fact.

Compare the automated labels with the adjudicated reference. Define the positive label explicitly. In the companion lab, positive means a defect is present. A false positive is acceptable content incorrectly flagged. A false negative is a defect the grader missed.

These errors have different consequences. Too many false positives create review burden and reduce trust. False negatives allow poor content through. Precision tells you how often flags correspond to reference defects. Recall tells you how many reference defects the grader caught. The acceptable tradeoff depends on the failure cost and the review workflow.

Repeatability is another question. Run the evaluator several times on unchanged inputs and preserve the configuration. Then inspect whether decisions change, especially near the release boundary. Repeated runs of the same scenario should not be counted as independent evidence about a broader user population.

Agreement metrics also need context. Raw agreement can look high when nearly every example belongs to one class. Cohen's kappa accounts for agreement expected from the raters' label proportions, but it is sensitive to prevalence. Neither statistic replaces examining critical misses and performance by content type.

When improving the grader, keep a separate evaluator test set. If you repeatedly tune criteria against the same examples, the score can improve without demonstrating broader reliability. Document what changed and what remains uncertain.

Try it: Run the bundled script, inspect each false positive and false negative, and propose one rubric change. Evaluate that change on fresh examples before declaring improvement.

Reference: van der Lee et al. (2019) reviews variation in human evaluation and argues for more consistent procedures. The local lab's metrics are diagnostic teaching tools, not validated release standards.

Make the Content Workflow Reproducible

By Sharmila Das

A successful prompt in a chat window is useful evidence that an approach might work. A repeatable workflow requires more: identifiable inputs, versioned instructions, preserved outputs, explicit errors, and a way to connect decisions back to evidence.

Start with the run record. Save the scenario ID, source version, prompt version, model identifier, configuration, output, and evaluator version. If a result changes, these fields help determine whether the cause was a prompt edit, different context, model behavior, or a grading change.

Keep generation separate from evaluation. The component that produces a message should return the message and operational metadata. Another step checks its shape and constraints. A semantic review examines usefulness and factual support. This separation makes it easier to diagnose failures and replace one component without rebuilding everything.

Schema checks are helpful but narrow. A JSON object can contain every required field and still make an unsupported claim. A length check can confirm that a message fits while missing that its action is inappropriate. Treat these checks as evidence about specific properties.

Failures belong in the dataset. A timeout, refusal, malformed response, or missing output should have an explicit status. Silently discarding those records makes the remaining sample look better than the full workflow. Report operational success alongside content quality.

The engineering contract should also cover retries, budget limits, duplicate prevention, access controls, and logging. Some failures are transient; others need a person. Repeatedly retrying an invalid request can add cost without increasing reliability.

A small local harness is a useful starting point. The companion script reads saved labels, checks a simple character constraint, and calculates agreement and confusion metrics. It deliberately makes no model calls. This lets a learner inspect the evaluation mechanics before adding network behavior and credentials.

For a portfolio, make the boundary explicit: “I built and tested the local evaluation harness; the provider adapter is a proposed next step.” That statement is more credible than presenting pseudocode as a deployed integration.

Try it: Add a run manifest and one explicit failure record to a saved-output exercise. Explain how your report includes that failure and how an engineer could reproduce the run.

Reference: OpenAI's structured output guide explains schema-constrained responses. The workflow contract above is a teaching design; use current provider documentation for a live implementation.

Design for a Meaningful Next Step

By Sharmila Das

Discovery, onboarding, and notifications operate at different moments. Discovery helps someone recognize a useful possibility. Onboarding helps them begin. A notification asks them to interrupt something else. Applying one “engaging” tone to all three misses the decision each message must support.

For discovery, make the value concrete. A fictional writing product might offer “Turn rough notes into a first draft.” The person can judge whether that is relevant. “Unlock your creativity” leaves the actual benefit harder to assess.

For onboarding, connect the promise to an achievable action. “Paste a paragraph to begin” tells the person what to supply. If there is a necessary choice or limitation, explain it at the point it matters. The goal is an understandable first success, not completion of a tour.

Notifications require another layer of judgment. Even useful words can be wrong when the trigger is stale, the person already completed the task, or the preview reveals something sensitive. A notification design needs eligibility, timing, frequency, expiration, and destination rules alongside the copy.

Consider “Your export is ready.” Before sending, the system should know an export actually completed, that the person requested it, that the message is still relevant, and that its link leads to the correct place. If those conditions fail, rewriting the sentence does not fix the experience.

Measurement should follow the user purpose. A high click rate may indicate curiosity or confusion. For onboarding, examine completion of a meaningful task and whether the person understood the action. For notifications, examine useful task completion alongside opt-outs, complaints, and interruption burden.

A portfolio exercise can make these tradeoffs visible without claiming a production launch. Create a fictional journey, write alternatives, document no-message conditions, test comprehension with consenting participants, and state what would need an online experiment.

Try it: Write one discovery card, one onboarding message, one recovery message, and one notification for the same fictional product. For each, specify the user state, intended action, failure condition, and measurement. Write a fifth example in which the correct decision is to send nothing.

Method note: These examples and recommendations are original product-design exercises aligned to the supplied job description. They describe no actual OpenAI notification policy or product capability.

Make Content Quality a Shared Decision

By Sharmila Das

Evaluation becomes useful when it changes a decision. A dashboard can show a rising score while leaving a team uncertain about what to ship, who should fix failures, or which tradeoffs are acceptable.

Start by connecting the report to the user problem. “The candidate scored 10.4” is incomplete. “The candidate clarified the first action but introduced unsupported promises in two scenarios” gives the team something to assess. Include the denominator, affected surface, severity, and limitations.

Then separate evidence from explanation. An evaluation may show that recovery messages fail more often. It does not by itself establish whether the cause is poor source material, unclear instructions, retrieval failure, or a grading problem. State the root-cause hypothesis and the next test that could challenge it.

Assign responsibility around the decision. Content design can own communication criteria and reviewer guidance. Engineering can own integration, logging, and failure handling. Product can own prioritization. Research can help investigate comprehension. Data Science can help design and interpret experiments. Sensitive claims may require specialist review.

These responsibilities become concrete in a release memo. Describe what changed, which tests ran, what regressed, which critical failures remain, and how the team will monitor and reverse the change. Record the versions so a future reviewer can reproduce the decision.

Coaching strengthens this process. Ask designers to score examples independently before discussing them. Compare the evidence behind their judgments. Revise an unclear criterion, test it on a new example, and capture the lesson. This teaches people to reason about quality instead of memorizing a preferred sentence.

A reusable approach should preserve its limits. A rubric that worked for documentation transformation may need different anchors for consumer notifications. A threshold chosen for a learning exercise should not quietly become a production policy. Document where an approach applies and where fresh validation is needed.

For a portfolio, include a decision memo and workshop agenda alongside prompts and results. They demonstrate the ability to turn individual expertise into a working team capability.

Try it: Write a one-page release recommendation with three sections: evidence, decision, and next validation. Include one reason to hold the candidate and one observation that could change the decision.

The Content Designer's Prompt & Evaluation Toolkit

Sharmila Das | October 2026

1. Begin with a content-design brief

Before writing a prompt, decide what the person needs to understand or do.

Field Fill in
User and situation Who is here, and what happened immediately before this message?
User job What meaningful next step should become easier?
Surface Discovery card, onboarding step, error, help answer, or notification
Source of truth Approved facts, capability limits, required prerequisites, and owner
Success Comprehension/task outcome, not only copy preference
Constraints Space, accessibility, language, timing, consent, and localization
Failure cost Confusion, lost work, unsupported claim, privacy exposure, interruption
No-message condition When should the system stay silent or ask a clarifying question?
Measurement Primary measure, guardrails, and evidence needed

Teaching brief: a fictional writing assistant helps a new user revise a paragraph. The user needs an understandable starting action. Approved capabilities: revise user-provided text and suggest tone changes. It cannot guarantee grades, jobs, accuracy, or publication success. This is a fictional product, not a description of current ChatGPT functionality.

2. Reusable prompt specification

Use this structure for documentation transformation, onboarding, or lifecycle messages. Store stable instructions separately from variable input. Treat source text as data; instructions embedded in it do not override the task.

PROMPT ID: onboarding_paragraph
VERSION: v1
TASK: Write one onboarding message for a first-time user.
USER JOB: Start revising a paragraph they supply.
APPROVED FACTS:
- The fictional product can suggest revisions to supplied text.
- The user reviews suggestions before choosing what to keep.
SOURCE BOUNDARY: Do not invent capabilities, outcomes, or personal facts.
CONTENT RULES:
- State a concrete next action.
- Use plain language and preserve user choice.
- Do not imply that the system has read content the user did not provide.
- If facts are insufficient, set needs_review=true and explain the gap.
INPUT:
audience={{audience}}
surface={{surface}}
approved_context={{approved_context}}
OUTPUT: JSON object with title, body, cta, needs_review, review_reason.
LIMITS: title <= 40 characters; body <= 140; cta <= 24.
EXAMPLE:
title: Try a paragraph
body: Paste a paragraph and choose what you want to improve. Review the suggestions and keep what works for you.
cta: Add a paragraph
needs_review: false
review_reason: ""

These character limits are exercise constraints. Count consistently in the UI and validator; Python's len counts Unicode code points, which may differ from visible characters or a platform's counting rules.

3. Prompt iteration without guessing

  1. Freeze a baseline and save its outputs.
  2. Tag the failure: missing step, unsupported fact, tone, relevance, length, format, or context.
  3. Write one hypothesis: “An explicit prerequisite rule will reduce missing setup steps.”
  4. Change one meaningful component when practical. Record unavoidable coupled changes.
  5. Rerun the same development examples with matching configurations.
  6. Review regressions, including cases that previously passed.
  7. Freeze the candidate before a held-out evaluation. If you use held-out results to revise it, retire that set into development and obtain fresh holdout cases.

Prompt log: ID, version, owner, change, hypothesis, dataset version, model/configuration, run time, defect counts, decision, limitations. Use templates/prompt_register.csv.

For documentation transformation, add immutable elements: commands, parameter names, technical terms, warnings, prerequisites, source IDs, and version scope. Ask for an issue report when preservation is impossible. Do not make the model silently “repair” unknown technical facts.

4. Content quality rubric

Use separate dimensions and written anchors. Do not average away a severe failure.

Dimension 0: fails 1: needs revision 2: meets brief
Grounding Invents a capability/fact Ambiguous or weak support Every material claim supported
Task usefulness Wrong or absent action Action needs interpretation Action fits the user's next step
Clarity Meaning unclear Understandable with effort Direct and easy to understand
Context Wrong state/audience Generic but usable Fits state and surface
Voice Pressure, blame, or misleading confidence Uneven tone Respectful, specific, appropriate
Accessibility Essential meaning unavailable Avoidable jargon/ambiguity Understandable without hidden context

Exercise hard gates: unsupported capability, private information disclosure, misleading outcome guarantee, and notification sent without required eligibility. A hard-gate failure blocks release even if other scores are high.

Suggested exercise decision: all hard gates pass; each dimension >=1; total >=10/12. This is a learning threshold, not a validated production standard. If dimensions conflict, document the tradeoff and decision owner.

5. Dataset design

The unit of evaluation is one scenario plus its generated message, source context, and expected behavior. Multiple model runs for one scenario are repeated observations, not independent new users.

For the capstone, author 60 scenarios: 30 development, 10 reviewer-calibration, and 20 held-out. Assign entire scenario families to one split to prevent near-duplicate leakage.

Suggested surface coverage: discovery, onboarding, notification, recovery, and re-engagement. Add sparse context, conflicting facts, long inputs, sensitive details, already-completed tasks, ineligible notifications, and accessibility needs.

Do not use a single “golden answer” when several wordings are acceptable. Specify constraints and acceptable behaviors. Reference copy illustrates a solution; it is not necessarily the only valid answer.

Track provenance, source permission, risk, split, audience, surface, expected action, forbidden claims, eligibility, rubric version, and author. Use templates/dataset.csv. Synthetic cases help explore failures; they do not establish real-world prevalence.

6. Reviewer guide and calibration

Give each reviewer the user state, approved facts, message, rubric, and task. Hide prompt version and candidate identity where feasible.

Reviewer sequence:

  1. Read the scenario and sources.
  2. Mark hard-gate failures and quote the relevant evidence.
  3. Score each dimension independently.
  4. Assign pass/fail using the declared rule.
  5. Record defect type, rationale, confidence, and unresolved ambiguity.

Two reviewers first label the 10 calibration scenarios independently. Discuss disagreements after labels are locked. Revise unclear anchors, then label fresh examples. Preserve the original labels; do not report post-discussion consensus as independent agreement.

One person cannot simulate independent inter-rater reliability. If only you are available, do a delayed blind second pass and label it intra-rater repeatability.

7. Reliability worksheet

Distinguish four questions:

  • Repeatability: Does the same evaluator make consistent judgments on the same material?
  • Human agreement: Do independent reviewers apply the rubric similarly?
  • Automated validity against reference: Does a grader detect the defects experts identified?
  • Robustness: Does performance persist across surface, audience, input, and prompt variations?

For binary defect labels, “positive” means a defect is present:

  • TP: grader flags a defect and reference flags a defect.
  • FP: grader flags a defect but reference does not.
  • FN: grader misses a reference defect.
  • TN: neither flags a defect.
  • Precision = TP/(TP+FP); recall = TP/(TP+FN).
  • False-positive rate = FP/(FP+TN). This differs from 1-precision.

Raw agreement = agreements / paired items. Cohen's kappa = (observed agreement - expected agreement)/(1 - expected agreement), where expected agreement uses each rater's label proportions. Report undefined denominators as unavailable. Kappa is sensitive to prevalence and is not a sufficient release criterion.

Worked synthetic example: TP=8, FP=2, FN=2, TN=8 gives precision=80%, recall=80%, FPR=20%, and accuracy=80%. With balanced marginals and 80% observed agreement, kappa=0.60. These are teaching numbers.

The lab script calculates agreement/kappa for two independent reviewers and confusion metrics for a supplied grader against a separate adjudicated reference. It does not adjudicate disagreements itself. Report sample counts and inspect slices; do not treat a tiny sample as proof of production reliability.

8. Discovery, onboarding, and notifications

Moment Design question Fictional example Evidence to collect
Discovery Is value concrete and relevant? “Turn rough notes into a first draft.” Can users explain the benefit?
Onboarding Is the first action clear? “Paste a paragraph to begin.” First task completion; confusion
Recovery Can users regain control? “That file could not be read. Try a text file.” Recovery success; repeated errors
Return Is there a user-owned reason to come back? “Continue your saved draft.” Meaningful resumed work
Notification Is interruption justified now? “Your export is ready to download.” Completion; opt-outs; complaints

Notification policy template: trigger, evidence of value, consent/eligibility, channel, user timezone, quiet hours, frequency cap, expiration, duplicate suppression, completed-task suppression, sensitive-preview rules, destination, fallback, owner.

Teach “no notification” as a valid output. A polished message can still be wrong if timing or eligibility fails. Do not use guilt, fabricated urgency, or personal facts inferred without a valid basis.

9. Experiment brief

Hypothesis: context-specific onboarding copy helps new users complete a first meaningful task. Define eligible population, randomization unit, assignment duration, control, treatment, exposure event, completion event, denominator, attribution window, exclusions, and analysis owner before launch.

Primary metric: first meaningful task completion among assigned eligible users. Guardrails: complaints, abandonment, errors, opt-outs, and repeat usefulness where measurable. Click-through is diagnostic, not proof of value.

Have a data scientist estimate required sample and duration using baseline rates, minimum detectable effect, and traffic. Do not stop just because an early result looks favorable. Separate offline quality, usability findings, and causal online outcomes.

Offline exercise: manually test with consenting participants using neutral tasks. Report recruitment limitations and observational findings. Do not describe a simulated A/B comparison as an actual randomized production experiment.

10. Repeatable code and API handoff

Contract:

  • Inputs: scenario_id, source_version, prompt_version, model_id, configuration, user state, approved context.
  • Output: message JSON, request ID, model/configuration, timestamp, refusal/error status, latency, and usage when available.
  • Evaluations: schema and length checks, independent semantic review, eligibility checks, and versioned decision rule.
  • Storage: output/run IDs, dataset version, reviewer labels and evaluator version; exclude secrets and unnecessary personal data.
  • Operations: timeouts, bounded retries for transient failures, backoff, rate limits, partial failure records, budget caps, and duplicate protection.

Pseudocode:

load frozen scenarios and prompt
for each scenario:
  build request from approved context
  call chosen provider through a small adapter
  log response or explicit failure with run metadata
  validate output shape and deterministic constraints
  route semantic quality to calibrated review
join results by scenario_id + candidate + repeat_id
compare baseline and candidate; investigate regressions

Structured output helps constrain shape, not factual accuracy. Recheck current provider documentation before implementing the adapter. No live adapter is bundled; the supplied local harness starts from saved outputs and review labels.

11. Diagnose failures and recommend changes

Use templates/failure_log.csv.

Symptom Check first Possible intervention
Invented capability Source facts and retrieval Fix authority/context; constrain claims
Missing prerequisite Brief and preservation rules Add requirement/example; regression case
Good content rejected Grader/reference disagreement Clarify rubric; calibrate thresholds
Poor content accepted False-negative examples Add relevant defect tests; strengthen gate
Valid JSON, unusable copy Semantic criteria Add human usefulness review
Strong offline score, weak activation Journey friction and exposure Research product experience and measurement
Notification complaints Trigger and eligibility Fix policy before rewriting copy

Recommendation memo: finding → evidence and n → root-cause hypothesis → proposed change → owner → tradeoff → validation → release/hold decision. Say what would change your mind.

12. Release and team enablement

Release record: user problem; prompt/source/model/rubric versions; known failures; held-out results by slice; human-review agreement; critical misses; rollback conditions; owner and monitoring cadence. Exercise gates: no observed critical failures, review all disagreements, and document any unsupported generalization. Zero observed failures in a small set does not mean zero risk.

Partner responsibilities: Content owns brief/rubric/copy; Engineering owns integration and failure handling; Product owns prioritization; Research owns study design; Data Science owns experiment analysis; relevant specialists review sensitive claims.

Teach a 45-minute workshop: 5-minute brief, 10-minute independent scoring, 10-minute disagreement review, 10-minute prompt revision, 10-minute rerun and decision. Capture one reusable lesson and one unresolved question. Coach judgment rather than teaching people to maximize a score.
